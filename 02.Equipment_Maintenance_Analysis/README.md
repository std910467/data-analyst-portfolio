# 02. Equipment_Maintenance_Analysis

## 專案說明
使用 Microsoft Azure Predictive Maintenance 公開資料，練習工業設備的故障與維運分析。

專案目標是把多表維運資料（感測、錯誤、維修、故障、設備主檔）整理成可分析的結構，並從中觀察：
- 哪些機台較常故障
- 故障集中在哪些零件
- 不同機型／機齡是否有差異
- 錯誤與故障隨時間的變化

資料來源為微軟提供的維運練習資料（5 張表），表結構模擬真實維運情境，但非單一工廠原始數據。

這是轉職資料分析的第二個專案，流程同樣是：資料處理 → SQL 建表 → 分析 → 視覺化。

---

## 分析內容
- 機台故障排行與零件故障結構
- 機型（model）、機齡（age）與故障的關係
- 錯誤（error）與故障（failure）的分布與趨勢
- 月度維運概況（故障／維修／錯誤）

（成本、產能等欄位資料中未提供，本專案不進行成本 ROI 分析。）

---

## 資料處理
- 原始表：
  - `PdM_telemetry`：感測（電壓、轉速、壓力、振動）
  - `PdM_errors`：錯誤紀錄
  - `PdM_maint`：維修／零件更換
  - `PdM_failures`：故障更換
  - `PdM_machines`：設備主檔（model、age）
- 時間粒度：先統一到「每日 × 機台」
- 關聯鍵：`machineID` + 日期

---

## SQL 資料表設計

### 中間表
- `int_daily_machine_summary`：每日 × 機台  
  彙總當日感測平均值、維修次數、故障次數、錯誤次數，並帶入機型與機齡

### 分析表（Mart）
- `mart_machine_failure_summary`：每台機器彙總（誰常壞、零件／錯誤結構）
- `mart_monthly_failure`：每月 × 機型彙總（趨勢與機型差異）

部分零件的故障更換占比偏高，顯示其更換較常由故障驅動，而非計畫性更換。後續可列為重點關注零件；至於要提高預防更換，或維持備品＋故障更換，需搭配停機成本與產線影響才能決定。
四類零件的更換次數接近，但故障占比不同。comp2 故障次數與故障／更換比皆最高，顯示其更換較常由故障驅動；comp3 則相對最低。後續可優先關注 comp2 的故障模式與出現機台，是否集中在 model1／model2 的高故障機。


在進行故障預測分析前，先針對故障事件進行資料清理。
由於同一設備可能在短時間內重複發生相同零件故障，為避免將同一問題重複計算，先針對連續發生的故障進行去重處理。

此外，資料中也觀察到同一天可能出現多個不同零件（component）的故障事件，這會導致故障前特徵難以歸因至單一零件，因此在本次分析中先將多重故障事件排除，以確保分析的解釋性。

在完成資料清理後，本次先聚焦於故障次數最高的 comp2，針對其所有故障事件，往前抓取數天的設備狀態（如 error 次數與 telemetry 指標），分析故障前的行為特徵。
將每次comp2故障抓出來，經過初步計算至少下次故障至少30天以上，所以可以將故障前三天整合資料作為實驗組，前4-6天的資料作為對照組，比較差異，可以發現轉速平均下降10%，然後開始出現error2、3



其他零件（comp1 / comp3 / comp4）則保留作為後續延伸分析。
